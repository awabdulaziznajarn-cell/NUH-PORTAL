# ١ · حرج — قبل الإطلاق

### ١.١ ✅ `Otp:Mode = "Static"` في الإنتاج — تجاوز كامل للهوية
`appsettings.Production.json` · `Services/OtpFlowService.cs` · `Controllers/OtpController.cs` ‏`[AllowAnonymous]`

الرمز الثابت `123456` يُقبل من أي أحد. مسار الهجوم كامل:

```
POST /api/Otp/send   { mobile: <جوال أي طالب> }
POST /api/Otp/verify { code: "123456" }
→ توكن صالح ٨ ساعات باسم الطالب
→ قراءة طلبه وبياناته الشخصية، وإعادة تقديمه، وتوقيع تعهّده
```

**الإصلاح:** `"Sms"` — **وإضافة رفض إقلاع**: التطبيق يجب أن يفشل في البدء لو `Mode == "Static"` خارج التطوير. الإعداد وحده يُنسى؛ الرفض لا يُنسى.

### ١.٢ ✅ الأسرار الحيّة في ملفات مرفوعة على git
`appsettings.Production.json` · `appsettings.Development.json` · `appsettings.json`

أربعة أسرار: كلمة مرور SQL · مفتاح توقيع JWT · ملح OTP · **كلمة مرور حساب الخدمة في الدومين** (الحساب الذي يُنشئ ويحذف مستخدمي AD).

نقطتان تزيدان الخطورة:
- **Development و Production بهما نفس القيم** — فبيئة التطوير ليست نطاق انفجار منفصل.
- مفتاح JWT معروف = تزوير توكن أدمن بلا كلمة مرور.

**الإصلاح:** نقل لمتغيّرات بيئة أو `appsettings.Production.local.json` (مستثنى في `.gitignore`) · **تدوير الأربعة** · تنظيف تاريخ git.

### ١.٣ ✅ **نطاق الجنس غير مطبَّق على الاستعلامات المفردة** ← أخطر اكتشاف جديد

القاعدة موجودة (`Core/GenderScope.cs`) ومطبَّقة على **القوائم**، ومغيبة عن **الجلب بالمعرّف**. تحقّقت بنفسي:

```csharp
// Services/StudentService.cs
:117  .ForGender(UnitOfWork.GetGenderScope())   ← القوائم ✔
:144  .ForGender(scope)                          ← الإحصاءات ✔
:151  .ForGender(scope)                          ← ✔

:196  GetByStudentNumberAsync  →  FirstOrDefaultAsync(s => s.student_id == trimmed)   ✘ بلا نطاق
:243  UpdateAsync              ✘   :321 DeleteAsync   ✘   :359 GetLifecycleAsync   ✘
```

**السيناريو:** مشرف القسم الطلابي يفتح `GET /api/Students/by-number/<رقم طالبة>` — يقرأ سجلها كاملًا (الهوية والجوال)، و`PUT /api/Students/{id}` يعدّله. الشاشة لا تعرضها له، والـ API يعرضها.

⚠️ وبلاغات مماثلة لم أتحقّق منها فرديًّا، في نفس النمط:
`RequestService.GetDetailsAsync` · `ReviewAsync` · `WorkflowActionService.RequireStagePermissionAsync` · `StudentStatusService.CreateCoreAsync` · `SupervisorHousingTransferService` · `HousingAccountService.ReProvisionAsync`

**الإصلاح المقترح:** بدل ترقيع كل دالة — قاعدة واحدة: **أي جلب لطالب أو طلب بالمعرّف يمرّ عبر دالة واحدة مغلّفة بالنطاق**، والوصول المباشر لـ `_students.Query()` يُمنع بمراجعة. ده اللي بيمنع رجوع العيب مع أول دالة جديدة.

# ٣ · تكرار — القاعدة مكتوبة في أكثر من مكان

> هذا القسم هو ما طلبته صراحةً. رتّبته بخطر الانحراف، والمهم فيه أن **بعضها منحرف بالفعل** — أي أن الشاشتين تعطيان إجابتين مختلفتين اليوم.

### ٣.١ ✅ قائمة «الحالات المفتوحة» — نسختان، **ومنحرفتان بالفعل**

```csharp
// Core/RequestWorkflow.cs — المصدر المشتق من جدول المراحل
public static string[] OpenStatuses => Transitions.Select(t => t.Status)
                                                  .Concat(new[]{ "need_more_info" })...

// Services/RegistrationService.cs — نسخة مكتوبة بالإيد، سبع حالات
{ "submitted", "pending_supervisor", "pending_cyber",
  "cyber_review", "cyber_approved", "ready_for_provisioning", "need_more_info" }
                                      ↑ "housing_approved" ناقصة
```

**الأثر:** هذه القائمة تحكم فحص التكرار. طالب طلبه في `housing_approved` (حالة حيّة) يقدر **يقدّم طلبًا ثانيًا**.
⚠️ ونفس السبعة مكتوبة ثالثة في `wwwroot/register/register-phone.html` وتعليقها يقول «نفس قائمة الخادم».

**البيت الصحيح:** `RequestWorkflow.OpenStatuses`، وتُحقن للواجهة مع باقي بيانات المراحل.

### ٣.٢ ⚠️ «أي حالة تعني مرفوض» — ٦ نسخ
`RequestWorkflow` (البيت المعلَن) · `WorkflowActionService` · `RequestTrackingService` · `RegistrationFlowService` · `request-details-page.js` · `track-request.html`.

✅ **تحقّقت:** `RequestService.cs:394` يكتب الشرط بحالتين فقط (بلا `cyber_rejected`).
**لكن** — قرأت السياق: الشرط لا يُفعّل إلا حين `CyberReviewedAt == null`، وحالة `cyber_rejected` تعني أن الأمن السيبراني كان طرفًا فعلًا. **فالأثر العملي معدوم اليوم.** يبقى تكرارًا يستحق التوحيد، لا ثغرة.

*(ذكرتُ هذا التفصيل عمدًا: لو نقلتُ البلاغ كما وصلني لقلتُ لك «تسريب ملاحظات» وكان غلطًا.)*

### ٣.٣ ⚠️ عدّادان مختلفان لحالات الطلبات — **منحرفان**
`RequestService.GetStatsAsync` يستعمل `RequestWorkflow.Aliases()`؛ `StudentService` يكتب الدمج بالإيد. الفروق: `completed` يشمل `approved` في واحد دون الآخر، و**لا يوجد صندوق `rejected` أصلًا** في الثاني. نفس الطلب، رقمان على شاشتين. وشاشة الرئيسية تجمع تعريفًا **ثالثًا** بنفسها.

### ٣.٤ ⚠️ قواعد الهوية والجوال — مكرّرة ونصوصها **متناقضة**
`Core/IdentityRules.cs` هو البيت، و`StudentService.Validate` يعيد كتابتها. الرسالة في الخادم تقول «يبدأ بـ 9665 ويتكوّن من ١٢ رقمًا»، والخانة في الواجهة ترفض ذلك وتطلب ٩ أرقام تبدأ بـ ٥. **المستخدم يُطلب منه ما لا تقبله الخانة.**
ورقم الهوية الوطنية: `FacultyHousingService` يشترط ١٠ أرقام تبدأ بـ ١ أو ٢، و`StudentService` يقبل أي ١٠ أرقام، والواجهة تكرّر النمط في ٥ ملفات.

### ٣.٥ ⚠️ `escHtml` — ١٣ نسخة، اثنتان أضعف
إحدى عشرة نسخة تُهرّب `& < > " '`، ونسختان (`request-details-page.js` · `reports-page.js`) تُسقطان `'`. والأسوأ أن نسخة صفحة تفاصيل الطلب **تحجب النسخة الأقوى** في التخطيط المشترك.

### ٣.٦ ⚠️ CSS مكرّر بقيم مختلفة
`.btn` و`.card` و`.content` و`.btn-primary` معرَّفة في `site.css` و`portal.css` بقيم مختلفة؛ و`.field` في `portal.css` و`components.css` بقيم مختلفة — و`register-form.html` **يحمّل الاثنين**، فيَنتج شكل هجين صامت.

### ٣.٧ ⚠️ متفرقات
قائمة المباني الصالحة مكتوبة في الكود بينما مصدرها جدول قابل للتحرير من شاشة القوائم المرجعية (إضافة مبنى ٧١ = يظهر في القائمة ويُرفض عند الحفظ) · جدول ترجمة الجنس مكتوب ٤ مرات داخل ملف واحد بثلاث دلالات فشل مختلفة · خريطة ألوان شارات السجل منسوخة حرفيًّا في مكانين · تنسيق التاريخ بعشر طرق مختلفة، اثنتان منها على **نفس البيانات** تعطيان `dd/MM` و`MM/dd`.

### يحتاج قرارك — لا تُحذف بلا رأيك

- **سلسلة المرفقات كاملة** — صفر استدعاء من أي شاشة، **لكن** الجدول حيّ في قاعدة البيانات، وصلاحية `requests.attachments` معرَّفة وممنوحة، و`Program.cs` يوثّق المسار كطريق معتمد للملفات المحمية. الشكل شكل **ميزة مبنيّة ولم تُوصَّل**، لا كود مهجور. حذفها يُسقط جدولًا.
- **`ADSetupController` + خدمته** — أدوات تشخيص للدومين (`readiness` · `dry-run` · `test-user`)، غالبًا تُستدعى يدويًّا وقت التركيب. اسأل فريق التشغيل.
- **`POST /api/Auth/Login` و`SetPassword`** — صفر استدعاء من الواجهة، لكنهما السطح الوحيد لإصدار JWT وعليهما قاعدة تحديد معدّل. قد يعتمد عليهما تكامل خارجي.

### 🔴 ليس كودًا ميتًا — **عيب**
`IStudentStatusService.GetActionAttachmentAsync` بلا مستدعٍ **لأن الكنترولر ينقصه الأكشن**. شاشة تحديث حالة الطالب تبني الرابط `/api/student-status/{id}/attachment`، و`Program.cs` يعدّه مسارًا معتمدًا — **والرابط يرجّع ٤٠٤**. الإصلاح: أضف الأكشن، لا تحذف الدالة.
